### Scoped capability and concurrency follow-up

This section supersedes the prior account/type-binding blocker: external buyers **do not need a DBP account**. An invitation intentionally allows multiple response kinds (`interested`, `offer`, `declined`, `unsubscribe`) within its server-stored allowed-action scope. Identical responses acknowledge without mutation; changed offers are distinct. Closed/canceled/expired deals and opted-out buyers reject new responses (unsubscribe remains available), while an identical accepted response may receive acknowledgement only. Expired/revoked links always deny, including replay. A different logged-in DBP account neither changes nor inherits capability authority.

The new migration `20261002190115_buyermatch_response_scope.sql` adds an immutable capability UUID, environment and allowed actions. The opaque token hash references an immutable exposure binding deal, buyer and owner/workspace context; the RPC also verifies current deal ownership. Callers cannot supply replacement IDs. Expiry is checked again after obtaining the token lock. The transaction locks token, deal and buyer before semantic deduplication or mutation, so separate client operation keys and simultaneous submissions cannot duplicate identical offers/events. This replaces the API's separate pre-transaction replay lookup. The legacy private RPC delegates to the same validation with staging scope. Thus a literal requirement that a token cannot be used under a different account or for another allowed response type is **not satisfied**. Do not claim these restrictions or silently replace the existing invitation design. Token hashes must remain isolated in their own environment database; independent environment secrets are required.
